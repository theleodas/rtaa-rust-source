## 1. PROJECT OVERVIEW

### What is this project?

This is a Rust implementation of the **RTAA (Round-based Tag-based Aggregate Authentication)** and **RTAA+** cryptographic protocols built on the BLS12-381 elliptic curve. The code reproduces attack and repair tests and cost measurements described in an associated poster/research paper.

### What problem does it solve?

The project addresses the problem of **aggregate authentication in group settings** — specifically how a set of devices (parties) can each produce an authentication tag on their individual data, such that:

1. A **verifier** can efficiently check that the aggregate of all tags is consistent.
2. When verification fails, a **judge** algorithm can identify the misbehaving party.
3. The original RTAA+ protocol had a security flaw where the per-party audit proof (`rho`) was not bound to the tag, allowing certain attacks to go undetected. This implementation demonstrates those attacks and validates the proposed **fix** (binding the tag into the audit hash `H3`).

### Main objective

- Implement RTAA/RTAA+ protocols with the BLS12-381 pairing-friendly curve.
- Demonstrate known attacks on the original RTAA+ (`rho_old`, unbound tag).
- Validate the repaired RTAA+ (`rho`, tag-bound).
- Measure computational costs: wall-clock timing, pairing operation counts, and scalability across various parameters (number of parties μ, message vector dimension k, threshold key generation parameters ℓ and t).

#### 3.5 Round generation: `make_round()` (lines 123–172)

```rust
fn make_round(mu: usize, k: usize, ell: usize, t: usize) -> Round
```

This is the **setup and data generation** function:

1. **Threshold Key Generation (Pedersen-VSS)** (lines 127–155):
   - Generates `ell` dealers, each with random degree-`t-1` polynomial pairs `(a, b)`.
   - Computes Pedersen commitments: `C[d][u] = g1·a[u] + h·b[u]`.
   - Every party verifies every dealer's shares against commitments.
   - `t` parties reconstruct the shared secret `theta` using Lagrange interpolation at point 0.
   - Derives `alpha = H(theta, RND, GID)`.
   - Computes `gammas[j] = g1 · alpha^(j+1)` for `j = 0..k-1`.
   - Records `tkg_s`: wall-clock time for TKG.

2. **Per-device report generation** (lines 157–171):
   - For each of `mu` devices: generates key pair `(sk, pk)`, random message vector `m` of length `k`.
   - Computes `w = Σ m[j] · alpha^(j+1)` (inner product with powers of alpha).
   - Computes tag `τ = (H0(id) + g1·w) · sk`.
   - Computes both audit proofs: `ρ = H3(e, true) · sk` (fixed) and `ρ_old = H3(e, false) · sk` (original).
   - Records per-device auth time.

Returns a `Round` struct containing entries, gamma values, message vectors, and timing.

#### 3.6 `verify_full()` (lines 174–185)

Full verification of a round:
1. Checks ID uniqueness.
2. Verifies `Σ gammas[j] · (Σ m_i[j]) = g1 · (Σ w_i)` — the aggregation consistency check.
3. Runs `auth_check` on all entries.

## 5. EXPERIMENTAL METHODOLOGY

### Experiment 1: Security Attack Table (`security`)

- **Purpose:** Demonstrate that the original RTAA+ judge misidentifies or fails on certain attacks, while the fixed RTAA+ judge behaves correctly.
- **Parameters:** μ=4, k=20, ℓ=5, t=3 (fixed).
- **Attack scenarios:**
  - `swap_w`: Swap w values between P0 and P1.
  - `sub_tau`: Replace P0's tag with a random point.
  - `sub_tau_garbage_rho`: Replace P0's tag and both ρ proofs with random.
  - `swap_tau`: Swap tags between P0 and P1.
  - `garbage_rho`: Replace P0's ρ proofs with random (tag intact).
  - `malicious_P2`: P2 replaces their own tag and recomputes valid ρ proofs for the tampered tag.
- **Metrics:** Whether verify rejects, which party each judge variant blames.
- **Reproduction:** `cargo run --release -- security`
- **Results:** Stored in `security_rust.csv`.

### Experiment 2: Wall-clock Timing (`timing`)

- **Purpose:** Measure computational cost of verify, base judge, and RTAA+ judge as μ grows.
- **Parameters:** μ ∈ {5,10,20,40,80,160,320}, k=20, ℓ=5, t=3.
- **Variables:** μ (independent), various times (dependent).
- **Metrics:** Median of 3–7 repetitions of each operation.
- **Reproduction:** `cargo run --release -- timing`
- **Results:** Stored in `timing_rust.csv`.

### Experiment 3: Pairing Operation Counts (`counts`)

- **Purpose:** Count the exact number of Miller loops and final exponentiations for each judge variant.
- **Parameters:** Same μ sweep as timing.
- **Metrics:** Integer counts from the atomic counters.
- **Reproduction:** `cargo run --release -- counts`
- **Results:** Stored in `counts_rust.csv`.

### Experiment 4: k-Sweep (`ksweep`)

- **Purpose:** Measure cost sensitivity to message vector dimension k.
- **Parameters:** k ∈ {5,10,20,40,80,160,320}, μ=40, ℓ=5, t=3.
- **Metrics:** Auth per device, verify, and TKG times.

### 7.2 Static code review findings

#### Potential issues

1. **`edition = "2024"` requirement** (Cargo.toml line 4): This is the newest Rust edition. Users with older toolchains (pre-1.85) will fail to build. Consider noting the minimum Rust version in documentation.

2. **No `#[test]` functions**: The project has zero unit tests. All validation is done via `assert!()` calls within the experiment functions themselves. This means correctness is only verified when experiments run, not through standard `cargo test`.

3. **Single-file architecture**: All 290 lines are in `main.rs`. This is acceptable for a research prototype but limits reusability. No library crate is exposed.

4. **No error handling for CLI arguments**: Unrecognized arguments silently fall through to the default case (runs `security` + `timing`). No `--help` or usage message.

5. **Randomized outputs**: The `timing` experiment uses randomized data, so exact CSV values will differ between runs. The `security` experiment also generates random keys each run, but the structural results (which attacks succeed/fail) should be deterministic in outcome.

6. **`thread_rng()` for cryptographic randomness**: While `thread_rng()` uses a CSPRNG internally (ChaCha20), in a production system one might prefer `OsRng`. For benchmarking purposes this is fine.

7. **Potential integer overflow in `invalid_rho()`** (line 269): The expression `(i * mu) / m.max(1) + 1` could theoretically overflow for very large values, but with the hardcoded parameters this is safe.

8. **No `Cargo.lock` in `.gitignore`**: For a binary crate (not a library), including `Cargo.lock` is **recommended** by Rust convention, so this is correct behavior. If this were a library crate, `Cargo.lock` would typically be excluded.

#### Code quality observations

- Code is **well-structured** with clear separation of protocol logic and experiments.
- Variable naming follows cryptographic conventions (`sk`, `pk`, `rho`, `tau`, `theta`, `alpha`).
- The `pairing_check` instrumentation via atomic counters is a clean design for counting without changing logic.

## 8. RESEARCH RELEVANCE

### Research problem

This implementation addresses the security of **Round-based Tag-based Aggregate Authentication (RTAA)** protocols, specifically the correctness and efficiency of the **judge** (dispute resolution) mechanism in RTAA+.

### Implemented methodology

The code implements:

1. **RTAA protocol** using BLS12-381 bilinear pairings:
   - Pedersen-VSS threshold key generation for deriving shared secrets.
   - Per-device authentication via BLS-like tags: `τ = (H0(id) + g1·w) · sk`.
   - Aggregate verification via multi-pairings.

2. **RTAA+ judge mechanism** in three variants:
   - **Base judge** (`judge_base`): Binary search for the misbehaving party.
   - **Original RTAA+ judge** (`judge_plus_orig`): Per-party audit with unbound ρ, then base judge.
   - **Fixed RTAA+ judge** (`judge_plus_fixed`): Per-party or batched audit with tag-bound ρ, filter invalid, then base judge. Returns ⊥ if no data-level cheating.

3. **The security fix**: Binding the tag into the H3 hash used for audit proofs, preventing attacks where an adversary can substitute tags while keeping valid audit proofs.

### Experimental evidence available

| Evidence | Status |
|----------|--------|
| Security attack table showing fix correctness | ✅ Present (`security_rust.csv`) |
| Wall-clock scaling with μ | ✅ Present (`timing_rust.csv`) |

| Sensitivity to message dimension k | ✅ Present (`ksweep_rust.csv`) |
| TKG cost scaling | ✅ Present (`tkgsweep_rust.csv`) |
| Robustness to invalid audit proofs | ✅ Present (`invalid_rust.csv`) |

### Conclusions the results support

Based on the data in the CSV files:

1. **The original RTAA+ is vulnerable**: The `garbage_rho` attack shows that the original judge incorrectly blames P0 when only P0's audit proof is corrupted (not their data). The fixed judge correctly outputs ⊥.

2. **The fix is correct**: In all attacks that involve genuine data corruption (`malicious_P2`), the fixed judge correctly identifies the cheater. In attacks that only involve structural manipulation without data fraud, it correctly outputs ⊥.

3. **Batched auditing is more efficient**: Batched judge uses significantly fewer final exponentiations than per-party judge (logarithmic vs. linear).

4. **Hybrid strategy is best for varying corruption levels**: The hybrid approach performs well whether zero or many proofs are corrupted.

5. **The protocol scales linearly**: All costs scale linearly with μ, and verification cost is dominated by the μ+1 pairing multi-product.
